# Working Agreement

Nexus Commerce uses Scrum adapted for one developer. Sprints are two weeks, subject to adjustment after capacity evidence. GitHub Projects and GitHub Issues are the source of truth for the Product Backlog and Sprint Backlog; Markdown does not duplicate the complete backlog.

## Goals and accountabilities

The Product Goal connects roadmap outcomes. Each Sprint has one Sprint Goal, and selected work forms the Sprint Backlog. For this individual project, the developer performs product, development, and facilitation responsibilities while deliberately separating prioritization, implementation, and review perspectives.

## Events

- **Sprint Planning:** choose a valuable goal and feasible work.
- **Daily Scrum:** a brief personal inspection of progress, blockers, and the next best action.
- **Backlog Refinement:** clarify and split future items; this is useful complementary practice, not a formal Scrum event.
- **Sprint Review:** inspect the increment and adapt the backlog using evidence.
- **Sprint Retrospective:** identify a small, actionable process improvement.

Code review may use self-review, delayed review, or external peer feedback. Branch conventions and pull requests preserve an inspection trail.

## Transparency

Status is based on repository and issue evidence. Unverified work is not marked complete. Architectural uncertainty is recorded as a Spike or Proposed ADR. See the [Definition of Ready](definition-of-ready.md), [Definition of Done](definition-of-done.md), and [estimation guide](estimation-guide.md).
